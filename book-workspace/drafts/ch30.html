Every cost model so far in this book has been denominated in FLOPs: the $C \approx 6ND$ of Chapter 24, the per-layer counts of Chapter 18, the optimizer overheads of Chapter 13. That currency is only convertible to wall-clock time when arithmetic is the binding constraint, and on a modern accelerator it almost never is. An H100 can execute roughly 295 bf16 FLOPs in the time it takes to move one byte to or from its own memory Verify; any operation performing fewer FLOPs per byte — which is every common deep-learning operation except large matrix multiplication — is limited by bandwidth, not arithmetic. This chapter builds the execution model and the roofline framework that make such statements precise, derives the arithmetic intensity of the transformer's constituent operations, and validates the method empirically. Chapters 31–34 are applications: FlashAttention, distributed training, inference serving, and quantization are all, at bottom, campaigns against the memory wall.

30.1 GPU Architecture for ML Engineers

A GPU is not a fast CPU; it is a different answer to the question of what to do with a fixed transistor and power budget. A CPU spends its budget making a few instruction streams fast: deep caches, branch prediction, out-of-order execution. A GPU spends it on arithmetic units and hides latency with parallelism instead of avoiding it with caches. The programming model reflects this. A kernel is launched as a grid of thread blocks; each block is assigned to one streaming multiprocessor (SM) and stays there until it finishes. An H100 SXM has 132 SMs Verify, each containing 128 FP32 ALUs, four schedulers, and four fourth-generation tensor cores.

30.1.1 Warps and SIMT

Within a block, threads are grouped into warps of 32 that execute in lockstep: one instruction, 32 data lanes (SIMT — single instruction, multiple threads). A warp is the true unit of execution and of memory access; when its 32 threads touch 32 consecutive 4-byte words, the hardware coalesces them into one wide transaction, and when they do not, bandwidth is wasted on unused bytes. Divergent branches within a warp serialize: both sides execute, with lanes masked off. Each SM scheduler holds many resident warps and issues from whichever is ready, so a warp stalled on a ~500-cycle HBM load Likely costs nothing if another warp can issue — latency is hidden, not eliminated. This only works if enough warps are resident, which is the occupancy question of Section 30.5.

30.1.2 Tensor cores: the 15× asymmetry

Tensor cores are systolic units that execute small matrix multiply-accumulates as single warp-level instructions. They are the only reason the headline numbers exist: the H100's bf16 tensor-core peak is 989 TFLOP/s dense, while its conventional FP32 vector ALUs peak near 67 TFLOP/s Verify — a factor of ~15. (Vendor marketing quotes 1,979 TFLOP/s, which assumes 2:4 structured sparsity; use dense numbers unless your weights are actually sparse.) The asymmetry has a hard consequence: only operations expressible as dense matrix multiplication can use the fast path. Softmax, normalization, activations, and optimizer updates run on the slow vector units — and, as we will see, they don't even saturate those, because they starve on bandwidth first.

30.2 The Memory Hierarchy and Its Bandwidths

The numbers that govern everything are the bandwidths of the memory ladder. Capacities shrink and bandwidths grow roughly an order of magnitude per level as you climb toward the ALUs.

Three readings of this table matter. First, "device memory" is the slow memory: HBM is where your tensors live, and it feeds the ALUs at roughly 1/300th of the rate they can consume operands. Fast kernels are therefore exercises in staging: copy a tile from HBM into shared memory once, reuse it many times from registers. Second, shared memory is software-managed — a scratchpad the kernel explicitly fills — unlike CPU caches; this is what makes the tiling of Section 30.5 possible. Third, energy tells the same story as time: an off-chip DRAM access costs on the order of 100× the energy of a floating-point multiply-add Likely (Horowitz's classic 2014 accounting), so the memory wall is also a power wall.

30.3 The Roofline Model

Definition 30.1 (Arithmetic intensity)

For a kernel that performs $W$ floating-point operations and moves $Q$ bytes between device memory and the chip, the arithmetic intensity is $I = W/Q$ FLOPs per byte. $Q$ counts actual traffic — reads plus writes, including intermediate tensors — not the size of the mathematical inputs.

Definition 30.2 (Machine balance)

For a machine with peak arithmetic throughput $\pi$ (FLOP/s) and memory bandwidth $\beta$ (bytes/s), the balance point is $B^* = \pi/\beta$ (FLOPs per byte). H100: $989 \times 10^{12} / 3.35 \times 10^{12} \approx 295$ for bf16 tensor-core work Verify; for FP32 vector work the relevant roof is $67/3.35 \approx 20$.

Theorem 30.1 (Roofline bound)

A kernel with work $W$ and traffic $Q$ satisfies $$t \;\ge\; \max\!\left(\frac{W}{\pi},\ \frac{Q}{\beta}\right), \qquad\text{equivalently}\qquad \frac{W}{t} \;\le\; \min\left(\pi,\ I\beta\right).$$ If $I < B^*$ the kernel is memory-bound: no optimization of its arithmetic can bring it to peak. If $I \ge B^*$ it is compute-bound.

Proof. The arithmetic units require at least $W/\pi$ seconds to issue $W$ operations; the memory system requires at least $Q/\beta$ seconds to move $Q$ bytes. Both are necessary, and even with perfect overlap of compute and data movement the runtime is at least the larger. Dividing $W$ by the bound gives the throughput form, since $W/(Q/\beta) = I\beta$. $\blacksquare$

The bound assumes perfect overlap, so it is optimistic; real kernels also pay launch overhead (~microseconds per kernel Likely), imperfect coalescing, and synchronization. But it is astonishingly predictive in the regime that matters, and its two failure directions are informative: a kernel far below both roofs is limited by something else — latency, occupancy, or overhead — which is exactly what a profiler should then be asked about.

Example 30.1 (Bias + GeLU on an H100, by hand)

Apply bias and GeLU to a $1024 \times 1024$ bf16 activation. Traffic: read $1024^2 \times 2 = 2.10$ MB, write $2.10$ MB, so $Q = 4.19 \times 10^6$ bytes (the bias vector's 2 KB is noise). Work: with the tanh approximation, roughly 10 FLOPs per element, $W \approx 1.05 \times 10^7$. Intensity: $I = W/Q = 10/4 = 2.5$ FLOPs/byte, against $B^* \approx 295$. Times: $t_{\text{mem}} = 4.19\times10^6 / 3.35\times10^{12} = 1.25\ \mu s$; $t_{\text{comp}} = 1.05\times10^7 / 6.7\times10^{13} = 0.16\ \mu s$ (vector roof). The memory term dominates 8:1 even against the slow ALUs — and 118:1 against a hypothetical tensor-core path. Making GeLU's arithmetic 10× faster would change nothing. Verify (H100 constants; the arithmetic is exact.)

30.4 Arithmetic Intensity of Common Operations

For a general matmul $(M\times K)(K \times N)$ in bf16, $W = 2MNK$ and the compulsory traffic is $Q = 2(MK + KN + MN)$ bytes, so $$I_{\text{matmul}} = \frac{MNK}{MK + KN + MN}\ \text{FLOPs/byte} \;\xrightarrow{\;M=N=K=n\;}\; \frac{n}{3}.$$ Intensity grows linearly with size: matmul is the one operation that can outrun any balance point. On an H100, square bf16 matmuls become compute-bound at $n/3 \ge 295$, i.e. $n \gtrsim 885$. At the other extreme, a matrix–vector product ($N=1$) has $I = MK/(MK+K+M) \approx 1$: two FLOPs touch every weight once, and no blocking can create reuse that the computation does not contain. Everything else in a transformer sits at the bottom of the same scale:

The attention row deserves its derivation, because it motivates all of Chapter 31. Computing $S = QK^\top$ for one head costs $W = 2n^2 d_h$ FLOPs; materializing $S$ to HBM writes $2n^2$ bytes, which dominates the traffic once $n \gg d_h$, giving $I \approx d_h$. With $d_h = 64$–$128$, unfused attention runs at a fixed intensity below the H100 balance point no matter how long the sequence is — and the softmax over $n^2$ scores then re-reads and re-writes the whole matrix at $I \approx 1$. Attention as naively implemented is a bandwidth program with some arithmetic attached. FlashAttention's insight (Chapter 31) is that never materializing $S$ removes the $n^2$ traffic entirely, restoring $I \propto n$.

30.4.1 Predicting a transformer layer

A transformer layer with width $d$ and a $4d$ MLP has $12d^2$ parameters ($4d^2$ in $Q,K,V,O$; $8d^2$ in the MLP), hence $24d^2$ bytes of bf16 weights and $W = 24d^2$ GEMM FLOPs per token (Chapter 18). Two regimes follow immediately from Theorem 30.1. In prefill / training, $t$ tokens are processed per weight-read, so the GEMMs run at intensity $\approx t$ per weight-byte and are compute-bound for $t \gtrsim 300$: predict $t_{\text{layer}} \approx 24td^2/(\text{MFU}\cdot\pi)$, where MFU (model FLOPs utilization) of 40–60% is typical of well-tuned training Likely. In batch-1 decode, each generated token reads every weight once: $I \approx 1$, memory-bound by 300×, and the prediction collapses to $t \approx \text{weight bytes}/\beta$ — arithmetic is irrelevant.

Example 30.2 (Decode latency of a 70B model, by hand)

A 70B-parameter dense model in bf16 occupies $70\times10^9 \times 2 = 140$ GB. Generating one token requires streaming essentially all weights through the ALUs once, so on H100-class HBM at $\beta = 3.35$ TB/s Verify: $t \ge 140/3350\ \text{s} = 41.8$ ms per token, i.e. at most $\approx 24$ tokens/s single-stream — regardless of compute. Check the compute term: $W \approx 2 \times 70\times10^9 = 1.4\times10^{11}$ FLOPs per token, $t_{\text{comp}} = 1.4\times10^{11}/9.89\times10^{14} = 0.14$ ms — 296× smaller, confirming $I \approx 1$ vs. $B^* = 295$. This single division explains why inference servers batch requests, cache KV, and decode speculatively (Chapter 33), and why quantization to 4 bits quadruples decode speed before it does anything else (Chapter 34).

The measured leg of objective 3 is Artifact 30.1: this book's build environment has no GPU, so the artifact makes these predictions for the CPU it runs on and validates them against wall-clock — large matmuls land within a few percent of the compute roof, and the memory-bound suite lands on the bandwidth roof. The method transfers verbatim to any GPU; only the two measured ceilings change.

30.5 Occupancy, Tiling, Tensor Cores

Why does matmul achieve its high intensity? The computation has $O(n^3)$ work on $O(n^2)$ data, but a naive triple loop still streams operands from HBM. The classical fix is tiling: each thread block computes a $T \times T$ output tile by iterating over the $K$ dimension in chunks, staging $T \times T_k$ slabs of $A$ and $B$ in shared memory; every staged element is reused $T$ times from on-chip storage, so HBM traffic per output falls by a factor of $T$ and effective intensity grows $\propto T$. Registers add a second tiling level: each thread accumulates a small sub-tile in registers, reusing shared-memory operands again. The ladder of Section 30.2 exists precisely to make this two-level reuse possible, and Hopper adds hardware to feed it (TMA asynchronous bulk copies into shared memory; warp-group MMA instructions that read tiles directly from shared memory) Verify.

Occupancy is the fraction of an SM's warp slots (64 on H100 Verify) that are resident. Since latency hiding requires ready warps, too-low occupancy leaves the memory pipeline idle between stalls. But occupancy trades against tiling: registers and shared memory are shared resources, so bigger tiles (more reuse, higher $I$) mean fewer resident blocks. Peak-performance kernels often run at 25–50% occupancy with large tiles Likely — occupancy is a means (enough parallelism to hide latency), not an end, and "increase occupancy" is bad advice for a compute-bound GEMM. Tensor cores add a final constraint: they consume operands in fixed small-matrix shapes, so problem dimensions that are not multiples of the tile granularity waste lanes on padding — one reason vocabulary sizes and hidden widths are chosen divisible by 64 or 128 (Chapter 23).

30.6 Kernel Fusion and Compilers

Consider a chain of $k$ elementwise operations applied to a tensor of $n$ elements — say scale, add-bias, activation, dropout-mask. Executed as $k$ separate kernels, each reads and writes $n$ elements: $Q_{\text{unfused}} = 2kn \cdot s$ bytes for element size $s$. Fused into one kernel, each element is read once, transformed $k$ times in registers, and written once: $Q_{\text{fused}} = 2ns$. The FLOPs are identical; the traffic falls by $k$; and since every such chain sits far below $B^*$, Theorem 30.1 predicts a speedup approaching $k\times$. Fusion is not an optimization of arithmetic at all — it is a refusal to launder intermediate values through HBM. The same logic yields fused softmax and normalization (one read, one write, per-row statistics kept on-chip, giving the "fused" intensities in the table above), GEMM epilogue fusion (bias and activation applied to the output tile while it is still in registers, making the elementwise work free), and, at the far end, FlashAttention, which fuses two matmuls and a softmax into one kernel (Chapter 31).

Doing this by hand for every operator chain is why compilers took over. torch.compile traces the graph and emits fused Triton kernels for elementwise-and-reduction regions; XLA does the equivalent for JAX. What compilers still cannot generally do is invent FlashAttention-grade algorithmic restructurings — fusing across a matmul requires changing the order of reductions and re-deriving numerical stability, which is Chapter 31's subject. Artifact 30.1 demonstrates fusion's limit case honestly: on its CPU, blockwise "fusion" of a 4-op chain yields only 1.33× because NumPy's per-element instruction overhead becomes the new roof — whereas torch.softmax, internally fused and threaded, beats the unfused NumPy softmax by 3.0× on identical data. Fusion buys exactly the distance between the traffic roof and the next constraint.

30.7 Profiling: What to Measure and What Lies

Three instruments, in order of increasing honesty: nvidia-smi, wall-clock timing, and a kernel profiler (Nsight Compute, torch.profiler). The first lies the most: its "GPU utilization" reports the fraction of time any kernel was resident, so a memory-bound kernel using 0.3% of peak FLOP/s shows 100% utilization. The number that tracks the roofline is MFU — achieved model FLOP/s divided by $\pi$ — which you compute yourself from token throughput and the analytic FLOP count (Chapter 24's $6ND$). Similarly, compare achieved bandwidth against the measured ceiling, not the spec sheet: a copy microbenchmark typically reaches only 85–93% of quoted HBM bandwidth Likely, and that measured number is the fair denominator — Artifact 30.1's first act is to measure both ceilings rather than trust any datasheet.

Common Pitfall

Timing GPU code without synchronization. Kernel launches are asynchronous: t0 = time.time(); y = model(x); t1 = time.time() measures the time to enqueue work, often microseconds for a computation taking milliseconds — a 1000× error that has produced many published "speedups." Call torch.cuda.synchronize() before reading both timestamps, or use CUDA events. Two further lies to control: the first call pays compilation, autotuning, and memory-pool growth (always warm up, then report a robust statistic — the artifact uses best-of-$k$, since interference on a shared machine is one-sided), and sustained runs downclock under power and thermal limits, so a 30-second benchmark can report 10–15% slower steady-state than a 100 ms burst Likely.

Artifact 30.1 — An Empirical Roofline Analyzer

This environment has no GPU, so the artifact builds a genuine roofline for the CPU it runs on rather than pantomiming one: it measures the machine's two ceilings (streaming bandwidth via 512 MiB copies sized past the 260 MiB L3; peak FLOP/s via a large sgemm), computes the arithmetic intensity of seven operations from their FLOP and byte counts, classifies each against the measured balance point, predicts runtimes via Theorem 30.1, and asserts that the classifications and compute-bound predictions hold. It then demonstrates fusion by cache-blocking a four-op elementwise chain. The identical procedure applies to any GPU — replace the two ceiling measurements and rerun.

"""Artifact 30.1 -- An empirical roofline analyzer for the machine it runs on.

No GPU exists in this environment, so we build the roofline for the CPU,
honestly: measure the two ceilings (streaming memory bandwidth via large
array copies, peak FLOP/s via large sgemm), compute each operation's
arithmetic intensity AI = FLOPs / bytes moved, classify it as compute- or
memory-bound against the measured machine balance point B* = peak/BW, and
predict its runtime as  t = max(FLOPs/peak, bytes/BW).  The identical
procedure applies verbatim to any GPU -- only the two ceiling measurements
change.  Pure NumPy core; torch appears only as a cross-check.
"""
import time
import numpy as np

rng = np.random.default_rng(0)

def tmin(f, reps=3):
    """Best-of-reps wall clock. Warm up twice first (page faults, BLAS
    thread pool spin-up, caches). Min, not mean: noise on a shared VM is
    one-sided -- interference only ever makes you slower."""
    f(); f()
    ts = []
    for _ in range(reps):
        t0 = time.perf_counter(); f(); ts.append(time.perf_counter() - t0)
    return min(ts)

# ---------------------------------------------------------------- ceilings
def measure_bandwidth():
    """STREAM-style copy, 512 MiB arrays (this VM has a 260 MiB L3, so the
    1 GiB working set streams from DRAM). Convention:
    count bytes read + bytes written, so a copy moves 2x the array size."""
    x = rng.random(2**27, dtype=np.float32); y = np.empty_like(x)
    t = tmin(lambda: np.copyto(y, x), reps=7)
    return 2 * x.nbytes / t                      # bytes/s

def measure_peak_flops():
    """Peak = best achieved large-sgemm rate. n=3072 is big enough to
    amortize overheads; 2n^3 = 58 GFLOP per call."""
    n = 3072
    a = rng.standard_normal((n, n), dtype=np.float32); b = a.copy()
    t = tmin(lambda: a @ b, reps=3)
    return 2 * n**3 / t                          # FLOP/s

BW   = measure_bandwidth()
PEAK = measure_peak_flops()
BSTAR = PEAK / BW                                # machine balance, FLOPs/byte
print(f"memory bandwidth (copy, r+w) : {BW/1e9:8.1f} GB/s")
print(f"peak compute (sgemm 3072^3)  : {PEAK/1e9:8.1f} GFLOP/s")
print(f"MACHINE BALANCE POINT B*     : {BSTAR:8.1f} FLOPs/byte")

# ---------------------------------------------------------------- op suite
# Each op: (name, callable-on-prealloc-buffers, flops, bytes moved by the
# implementation as written).  exp counted as 1 FLOP (roofline convention;
# its true cost shows up as memory-bound ops running above prediction).
R, C = 16384, 8192                                # 512 MiB: larger than L3
X  = rng.random((R, C), dtype=np.float32)   # uniform: cheap to generate
T  = np.empty_like(X); OUT = np.empty_like(X)
n1 = 2**27                                        # 512 MiB per fp32 array
xa = rng.random(n1, dtype=np.float32)
za = rng.random(n1, dtype=np.float32); ya = np.empty_like(xa)
G  = {n: rng.standard_normal((n, n), dtype=np.float32) for n in (512, 1024, 2048)}
GB = {n: G[n].copy() for n in G}
nv = 16384                                        # 1 GiB matrix: DRAM-resident
Av = rng.random((nv, nv), dtype=np.float32)
xv = rng.random(nv, dtype=np.float32)

def softmax_rows():        # 5 unfused kernels, 7 full passes over R*C floats
    m = X.max(axis=1, keepdims=True)             # read X
    np.subtract(X, m, out=T)                     # read X, write T
    np.exp(T, out=T)                             # read T, write T
    s = T.sum(axis=1, keepdims=True)             # read T
    np.divide(T, s, out=OUT)                     # read T, write OUT

def layernorm_rows():      # 5 unfused kernels, 8 full passes
    mu = X.mean(axis=1, keepdims=True)           # read X
    np.subtract(X, mu, out=T)                    # read X, write T (T = x-mu)
    np.multiply(T, T, out=OUT)                   # read T, write OUT (scratch)
    v = OUT.mean(axis=1, keepdims=True)          # read OUT
    np.multiply(T, 1.0/np.sqrt(v + 1e-5), out=OUT)  # read T, write OUT

ops = []                   # (name, fn, flops, bytes)
for n in (512, 1024, 2048):
    ops.append((f"matmul {n}^3", (lambda n=n: G[n] @ GB[n]), 2*n**3, 12*n**2))
ops.append((f"matvec {nv}^2", (lambda: Av @ xv), 2*nv**2, 4*(nv**2 + 2*nv)))
ops.append(("triad y=2x+z", (lambda: np.add(np.multiply(xa, 2.0, out=ya), za, out=ya)),
            2*n1, 12*n1))
ops.append((f"softmax {R}x{C}", softmax_rows, 5*R*C, 7*4*R*C))
ops.append((f"layernorm {R}x{C}", layernorm_rows, 7*R*C, 8*4*R*C))

print(f"\n{'op':<20}{'AI':>7}{'bound':>9}{'pred ms':>9}{'meas ms':>9}"
      f"{'meas/pred':>10}{'%peak':>7}")
results = []
for name, fn, flops, byts in ops:
    ai    = flops / byts
    bound = "compute" if ai >= BSTAR else "memory"
    pred  = max(flops / PEAK, byts / BW)          # the roofline prediction
    meas  = tmin(fn)
    frac  = flops / meas / PEAK                   # fraction of peak achieved
    results.append((name, ai, bound, pred, meas, frac))
    print(f"{name:<20}{ai:>7.2f}{bound:>9}{pred*1e3:>9.2f}{meas*1e3:>9.2f}"
          f"{meas/pred:>10.2f}{100*frac:>6.1f}%")

# ------------------------------------------------------------- assertions
for name, ai, bound, pred, meas, frac in results:
    if bound == "memory":
        # A memory-bound op must be nowhere near the compute ceiling...
        assert frac < 0.35, f"{name}: 'memory-bound' but hit {frac:.0%} of peak"
        # ...and land within [1/3x, 4x] of the bandwidth prediction (above
        # 1x means unmodeled cost: exp, reduction overhead; below 1x means
        # a multithreaded BLAS kernel beat our single-thread copy ceiling,
        # as sgemv does here -- read-only streams parallelize well).
        assert 1/3 <= meas/pred <= 4.0, f"{name}: ratio {meas/pred:.2f}"
    else:
        # A compute-bound op must run near the ceiling: within factor 1.7.
        assert frac >= 0.35, f"{name}: 'compute-bound' at {frac:.0%} of peak"
        assert 1/1.7 <= meas/pred <= 1.7, f"{name}: ratio {meas/pred:.2f}"
print("\nall classification + prediction assertions passed")

# ---------------------------------------------------- fusion, demonstrated
# Chain of 4 elementwise ops on 512 MiB: y = relu(2x+1) * 3.
# Unfused: 4 kernels, each a full read+write pass over HBM-resident data.
# 'Fused': one loop over 256 KiB cache-resident blocks -- exactly what a
# fused GPU kernel (or torch.compile) does with registers/shared memory.
def unfused():
    np.multiply(xa, 2.0, out=ya); np.add(ya, 1.0, out=ya)
    np.maximum(ya, 0.0, out=ya);  np.multiply(ya, 3.0, out=ya)
def fused(blk=2**16):
    scratch = np.empty(blk, dtype=np.float32)
    for i in range(0, n1, blk):
        s = scratch[: n1 - i] if n1 - i < blk else scratch
        np.multiply(xa[i:i+blk], 2.0, out=s); np.add(s, 1.0, out=s)
        np.maximum(s, 0.0, out=s);            np.multiply(s, 3.0, out=ya[i:i+blk])
tu, tf = tmin(unfused), tmin(fused)
print(f"\nfusion: unfused {tu*1e3:6.1f} ms ({8*4*n1/tu/1e9:.1f} GB/s of traffic)"
      f" | fused {tf*1e3:6.1f} ms | speedup {tu/tf:.2f}x")
assert tf < tu, "fusion must win: same FLOPs, 4x less DRAM traffic"

# ------------------------------------------------------ torch cross-check
try:
    import torch
except ImportError:
    torch = None
if torch is not None:
    xt = torch.from_numpy(X)
    t = tmin(lambda: torch.softmax(xt, dim=1))
    print(f"torch.softmax (internally fused/threaded): {t*1e3:.1f} ms vs "
          f"numpy unfused {results[-2][4]*1e3:.1f} ms")
else:
    print("[skipped: torch not installed]")

if __name__ == "__main__":
    print(f"\nsummary: every op with AI below B*={BSTAR:.0f} FLOPs/byte was "
          "memory-bound in measurement; only large matmul was compute-bound.")

On this book's 4-core build VM the run measures $\beta = 19.8$ GB/s, $\pi = 494$ GFLOP/s, and prints MACHINE BALANCE POINT B* : 24.9 FLOPs/byte. The $2048^3$ matmul ($I = 341$) is predicted at 34.8 ms and measured at 35.1 ms — a ratio of 1.01 at 98.9% of peak — while every op with $I < B^*$ achieved under 5.2% of peak FLOP/s, exactly as classified: matvec measured 22.5 ms against a 54.2 ms single-thread prediction (multithreaded BLAS beat the one-thread copy ceiling, ratio 0.41), and softmax ran 2.33× over its bandwidth prediction (the unmodeled cost of exp and reduction overhead). The fusion demo saves traffic for a 1.33× speedup before NumPy's per-element overhead becomes the binding roof, while the fused, threaded torch.softmax cross-check runs in 148 ms against unfused NumPy's 441 ms. All assertions pass in about 29 s.

Key Takeaways
  • Runtime obeys $t \ge \max(W/\pi, Q/\beta)$: an operation whose arithmetic intensity $I = W/Q$ is below the machine balance $B^* = \pi/\beta$ is memory-bound, and no arithmetic optimization can save it. Certain
  • On current accelerators $B^*$ is roughly 150–300 bf16 FLOPs/byte (H100: $\approx$295), and every common deep-learning operation except sufficiently large matmul sits far below it — elementwise, softmax, and normalization near $I \approx 1$, unfused attention at $I \approx d_h$. Verify
  • Matmul intensity grows with size ($n/3$ for square bf16), which is why tiling through shared memory and registers — and the tensor cores it feeds — can reach peak; batch-1 decode is a matvec at $I \approx 1$ and is bounded by weight bytes over bandwidth (~42 ms/token for 70B bf16 on H100-class HBM). Verify
  • Fusing a $k$-op elementwise chain cuts HBM traffic by $k\times$ at identical FLOPs; fusion, epilogues, and FlashAttention are all the same idea — keep intermediates on-chip. Certain
  • Profile against measured ceilings, not spec sheets or "GPU utilization": compute MFU from analytic FLOPs, synchronize before timing, warm up, and expect ~85–93% of quoted bandwidth to be attainable. Likely
