Appendix B

Environment Setup

This appendix is a build record, not a wish list. The book contains 42 artifacts — one per chapter, Chapters 1 through 42, across all eight parts — and every one of them was written to a file, executed, and re-executed until it ran clean before its output was quoted in the text. The versions below are the versions that produced those numbers. Nothing here was run on a GPU. Section B.1 states the machine, B.2 builds the environment, B.3 documents the numpy-only fallback that lets all 42 artifacts run with no PyTorch at all, B.4 runs them, B.5 covers seeding, B.6 covers Colab and Kaggle, B.7 and B.8 cover the companion ml-foundations exercise ladder and its encrypted tier, and B.9 fixes the offline mathematics.

Where the book says “torch 2.13.0, CPU,” it means the numerics of 2.13.0 executed on a CPU device, which is what a reader on the CPU wheel gets.

Consequence for the hardware numbers. Chapter 30 and Chapter 31 are full of memory bandwidths, tensor-core throughputs, SRAM capacities, and arithmetic intensities. None of those are measurements taken for this book. They are vendor specifications and published benchmark figures, and they are tagged accordingly: Chapter 30 alone carries 17 Verify tags out of 31 total tags, and Chapter 31 carries 10. Book-wide the count is 259 Verify tags against 339 Certain, 236 Likely, and 69 Contested. A Verify tag on a hardware number means exactly this: it was correct against the vendor’s datasheet when written, it was not reproduced here, and you should re-derive it on your own silicon before quoting it. What was measured on this machine are the artifact outputs, and those are CPU numbers about algorithmic behaviour — residuals, iteration counts, accuracy, relative timings — never absolute accelerator throughput.

B.2 A Minimal Virtual Environment

Four commands. The --index-url is the one line that matters: it selects the CPU wheel and skips the CUDA stack.

python3.11 -m venv ~/mlbook-venv
source ~/mlbook-venv/bin/activate
pip install --upgrade pip
pip install "numpy==2.4.6" "scipy==1.17.1" "scikit-learn==1.9.0"
pip install --index-url https://download.pytorch.org/whl/cpu "torch==2.13.0"

On Windows the activation line is ~\mlbook-venv\Scripts\activate; everything else is identical. Pin the exact versions on a first read. Once you have run the artifacts and seen what they print, unpin freely — nothing in the book depends on a private API. The one version boundary that does bite is numpy 2.x: numpy 2 changed integer promotion rules and removed several long-deprecated aliases, so an artifact run under numpy 1.26 can produce a different dtype in an intermediate and trip an exact-equality assertion. To confirm the environment before touching a chapter:

B.3 The CPU-Only Fallback Path

Every artifact’s core is pure numpy. PyTorch and scikit-learn appear only as cross-checks: an independent implementation to compare a from-scratch gradient, decomposition, or attention score against. Because they are cross-checks and not implementations, every one of them is guarded:

try:
    import torch
except ImportError:
    torch = None

# ... later, at the cross-check ...
if torch is None:
    print("  [skipped: torch not installed]")
else:
    ref = torch.linalg.lstsq(A_t, b_t).solution.numpy()
    print(f"  max|ours - torch| = {np.abs(w - ref).max():.3e}")

This was tested rather than asserted. All 42 artifacts were re-run in an environment where import torch and import sklearn both raise ImportError. All 42 exited zero, produced no traceback, and kept every from-scratch assertion live. The sweep printed 42 skip lines in total: 28 instances of [skipped: torch not installed], 8 of [skipped: no torch reference], and 6 of [skipped: sklearn not installed]. Certain

You can reproduce that test without uninstalling anything. Put two shadow modules on the path that raise on import:

mkdir -p /tmp/blocker
echo 'raise ImportError("blocked")' > /tmp/blocker/torch.py
echo 'raise ImportError("blocked")' > /tmp/blocker/sklearn.py
PYTHONPATH=/tmp/blocker python code/ch12_artifact.py

Chapter 12’s artifact then prints [skipped: torch not installed] where the cross-check would have been and exits zero with every signal-propagation assertion still checked. The practical upshot: if all you have is numpy, you can run this entire book. You lose the independent confirmation, not the content. Chapter 40’s artifact goes furthest — its only import is dataclasses from the standard library, so it runs on a bare Python install in 0.04 s.

B.4 Running the Artifacts

Each artifact is a standalone file with an if __name__ == "__main__": demo at the end. Run one:

python code/ch18_artifact.py

Run the whole set, timing each, and stop on the first failure:

for f in code/ch*_artifact.py; do
  /usr/bin/time -f "$f %e" python "$f" > "/tmp/$(basename $f).out" 2>> /tmp/timings.txt || echo "FAIL $f"
done

The full sweep of 42 artifacts took 248 s of wall clock on the otherwise idle 4-core machine of Section B.1 — just over four minutes for the entire book, interpreter startup included. Verify The slowest three are Chapter 35 at 27.0 s, Chapter 15 at 23.0 s, and Chapter 30 at 21.6 s; the median is 3.0 s. Every artifact fits inside the contract’s 30-second budget on an idle machine, but the top of that list has no margin left: put any other load on the same four cores and the slowest few cross it. None of them downloads anything, reads a dataset from disk, or touches the network. Every input is synthesized in-process. That is a deliberate constraint: an artifact that needs a corpus is an artifact that stops running the day the corpus moves.

Common Pitfall

Assertions that compare wall-clock timings are the ones most likely to fail on your machine, and they fail for reasons that have nothing to do with the mathematics. Chapter 17’s artifact carries one: assert pr > sr, that a single time-fused GEMM reaches higher throughput than the sequential per-timestep loop at every batch size. It holds on the build machine. Look at how little it holds by. At $T=512$, $d=256$, fp32, the fused path wins by 22.8× at $B=1$ — but at $B=32$, three consecutive runs of the same unmodified file on the same idle 4-core box measured gaps of 2.5×, 1.8×, and 1.5×. The margin fell by 40% with nothing changed but the run. The reason is structural: as $B$ grows, each per-timestep GEMM gets large enough for BLAS to run it near peak, so the sequential path climbs from 21 to 168 GFLOP/s between $B=1$ and $B=32$, while the fused call was already near peak and has nowhere to go. On a narrower or busier machine that margin reaches zero and the assertion fails — while the gradient checks in the same file still agree with torch.nn.LSTM to a relative error below $10^{-15}$. If an artifact fails for you, read the failing line first: if it is comparing milliseconds rather than residuals, your hardware disagrees with the build machine and the chapter’s argument is unaffected.

B.5 Determinism and Seeding

The book’s convention is a fresh, explicitly seeded generator, never the legacy global state:

rng = np.random.default_rng(0)          # yes
np.random.seed(0); np.random.randn(3)   # no — global, and legacy

default_rng(0) accounts for 53 of the 89 generator constructions across the 42 artifacts. The exceptions are deliberate: Chapter 14 needs independent replicates to show that a regularization effect is not a seed artifact, so it indexes them as default_rng(1), default_rng(2), default_rng(3), and so on, and the seed is the replicate index. Where an artifact needs a torch generator it passes one explicitly — Chapter 33 uses torch.Generator().manual_seed(0) rather than the global torch.manual_seed, so a cross-check cannot silently perturb the numpy stream that follows it.

Reproducibility has a hard boundary and it is worth naming. Given the same numpy version and the same seed, integer and structural results are bit-identical across machines. Floating-point results are not: BLAS reduces sums in an order that depends on thread count and on the kernel your CPU dispatches to, and floating-point addition is not associative (Chapter 5). Expect agreement to roughly $10^{-12}$ relative on a well-conditioned linear solve and much less on an ill-conditioned one, which is exactly the phenomenon Chapter 5 measures. To narrow the gap when comparing runs, pin the thread count before importing numpy:

export OMP_NUM_THREADS=1
export OPENBLAS_NUM_THREADS=1
export MKL_NUM_THREADS=1

This makes the reduction order deterministic on a single machine at a real cost in speed. It does not make results identical across different BLAS builds. Certain

B.7 Running the ml-foundations Ladder

The companion exercise repository is paced against the book: each exercise is a standalone file whose check() assertions at the bottom are the specification. The intended use is destructive — delete a function body, replace it with pass, re-read the docstring and the assertions, and reimplement until the checks pass. Reading an implementation and writing one are different skills and only the second transfers.

The harness is check.py at the repository root. It imports nothing but the standard library, deliberately, so that a failing exercise fails for its own reasons and never because the harness could not load. Two ways to run it:

python3 check.py              # every exercise, each as its own subprocess
python3 check.py tier0_math   # one tier
python3 tier0_math/ex01_linalg.py   # one exercise, directly

The runner executes each exercise as a subprocess, prints PASS or FAIL per file with the last six lines of output on failure, prints an n/m exercises passed summary, and exits non-zero if anything failed — so it drops into CI unchanged. Inside an exercise, check(name, got, expected=True, tol=None) defaults to exact comparison; pass a tol and it compares scalars and array-likes elementwise and reports the worst absolute difference, which is the number you actually want when a gradient check fails. summary() exits 1 if any check failed.

As of this writing all seven tiers exist and 17 exercises are written, so a full run on the machine of Section B.1 prints 17/17 exercises passed. Verify The bottom two tiers are complete: tier0_math has five (ex01_linalg through ex05_linear_models: matrix calculus, probability and entropy, gradient descent, floating point, linear models) and tier1_autodiff four (ex06_micrograd through ex09_optimizers: a scalar autodiff engine, a tensor one, initialization and normalization, optimizers). Above them the coverage is a skeleton: tier2_architectures has three (ex14_attention, ex15_transformer_block, ex16_rope), tier3_sequence two (ex17_linear_attention, ex18_ssm_scan), and tier4_llm, tier5_systems, and tier6_encrypted one each (ex24_dpo_grpo, ex26_speculative_decoding, ex29_poly_depth). The gaps in the numbering are the exercises the README’s tier table promises and that have not landed; check the repository rather than this page for what exists today.

The dependencies are lighter than that tier table suggests. Nothing in the ladder imports scipy. Every core implementation is numpy, and ex06_micrograd is pure standard library. torch appears in six files — two in tier 0, three in tier 1, one in tier 2 — and scikit-learn in exactly one (ex05_linear_models), always as a guarded cross-check under the pattern of Section B.3. Re-run the whole ladder with both blocked and it still prints 17/17 exercises passed: numpy alone runs every exercise that exists today. Certain The README warns that tier 4 targets a single small GPU and degrades to a tiny model on CPU; the one tier-4 exercise written so far is numpy and needs neither.

B.8 Tier 6: The Encrypted Exercises

Tier 6 is the join point between the ladder and Part VIII (Chapters 38–42): polynomial softmax and inverse square root, an encrypted linear layer, and depth budgeting. It is the only tier that will reach for dependencies the rest of the book does not have — but not yet. The one tier-6 exercise written so far, ex29_poly_depth, builds Chebyshev approximation and the multiplicative-depth ledger in numpy and imports no cryptographic library at all, on the grounds that the depth arithmetic is a scheme fact rather than a library fact. The installs below are for the exercises that will actually encrypt something.

# Python bindings over Microsoft SEAL — the fast path
pip install tenseal

# OpenFHE: C++ library, built from source
git clone https://github.com/openfheorg/openfhe-development.git
cd openfhe-development && mkdir build && cd build
cmake .. && make -j$(nproc) && sudo make install

TenSEAL is a wheel and usually installs in seconds. OpenFHE is a C++ build: budget real time for it, expect a working C++17 toolchain and CMake to be prerequisites, and note that the Python bindings live in a separate repository which must be built against the C++ library after it is installed. Common Pitfall

[VERIFY] — homomorphic-encryption library APIs move faster than any book. This is not a hedge; it is the single most reliable way to waste an afternoon. Context construction, parameter selection, key generation, the rescaling and level-management calls, and above all the bootstrapping setup have all changed names, signatures, or default behaviour across minor releases of both TenSEAL and OpenFHE. Any code sample in tier 6, in Part VIII, or in a blog post older than a few months should be treated as pseudocode that shows the shape of the computation. Before running it, open the library’s own examples/ directory at the version you installed: it is compiled and tested against the code, which makes it the only documentation that cannot drift. The concepts in Chapters 38 and 39 — multiplicative depth, level consumption, rotation counts, the cost of a Chebyshev approximation — are stable; the function names that express them are not.

One reassurance about the book proper: none of the 42 artifacts imports TenSEAL, OpenFHE, or any other HE library. Part VIII’s artifacts are counting models and numerical approximations in numpy — Chapter 38’s is an explicit depth-and-rotation ledger that never encrypts anything, Chapter 39’s works in numpy.polynomial.chebyshev, Chapter 40’s imports only dataclasses. You can read and run all of Part VIII with no cryptographic library installed. Tier 6 is where you would actually encrypt something, and it is optional.

B.9 MathJax, and Why the Formulas Might Be Raw LaTeX

The book is one self-contained HTML file with one external dependency, and this section exists because the page’s own failure banner points here.

Mathematics is typeset by MathJax 3, loaded from a CDN by a single line in the head:

<script id="MathJax-script" async
        src="https://cdn.jsdelivr.net/npm/mathjax@3/es5/tex-mml-chtml.js"></script>

If you are offline, behind a proxy that blocks cdn.jsdelivr.net, or reading from a USB stick on an air-gapped machine, that request fails and every formula in the book renders as raw LaTeX source — literal dollar signs and backslashes in the middle of otherwise normal prose. Nothing else on the page is affected: text, tables, code, and boxes are unaffected because they need no script. The page detects this. A status banner reads “Typesetting mathematics…” on load and hides itself when MathJax finishes; if MathJax has not initialized after 12 seconds, the banner rewrites itself to say so and points at this appendix rather than sitting there claiming to be working forever.

The fix is a local copy. Get the MathJax 3 package and put it beside the HTML file:

# with npm
npm install mathjax@3
mv node_modules/mathjax ./mathjax

# or without npm — fetch and unpack the published tarball
curl -LO https://registry.npmjs.org/mathjax/-/mathjax-3.2.2.tgz
tar xzf mathjax-3.2.2.tgz
mv package mathjax

Then edit the one line in the book’s head, changing the src attribute from the jsdelivr URL to the relative path mathjax/es5/tex-mml-chtml.js and leaving the rest of the tag alone. Do not delete the async attribute or the id; the banner logic keys off the loaded object, not the tag.

This was verified, not assumed. With MathJax 3.2.2 unpacked locally and the src rewritten, a headless Chromium loaded the book from a file:// URL, made zero network requests, hid the banner, and typeset 9,848 math elements in 24.7 s on the 4-core machine of Section B.1. Verify That is also the honest answer to “why is the page slow on first load”: typesetting time scales with the number of formulas, and a book with nearly ten thousand of them in a single document takes tens of seconds on a modest CPU whether the script came from a CDN or from disk.

The unpacked package is 24 MB, most of which the book never touches. If you are shipping the book somewhere size-constrained, two paths suffice: mathjax/es5/tex-mml-chtml.js (1.2 MB) and the directory mathjax/es5/output/chtml/fonts/ (500 KB). A tree containing only those two, 1.7 MB in total, rendered all 9,848 elements with zero failed requests in the same headless test. Verify Everything else in the package — the SVG output jax, the MathML input jax, the 3.9 MB speech-rule engine — is unused by this configuration.

Two smaller notes. Some browsers block file:// subresource loads under a strict local-file policy; if the local copy still fails, serve the directory with python3 -m http.server and open http://localhost:8000 instead. And if you only need the mathematics readable rather than beautiful, the raw LaTeX is not a disaster: $\mathcal{L}$, $\nabla_\theta$, and $\sigma(z)$ are legible as source, and the notation table in Appendix A is deliberately written so that each symbol is named in prose beside its glyph.
