Appendix C

Complete Code for All Artifacts

Every one of the 42 chapters ends in exactly one artifact, numbered N.1, and the listing printed inside that chapter’s artifact box is the complete file — not an excerpt, not a sketch with elisions. This appendix is therefore an index to those 42 programs rather than a second copy: one row per chapter giving the title, what it builds, what it checks itself against, and which libraries it needs. Section C.1 gives the arithmetic behind that decision; C.2–C.4 are the index, grouped by part; C.5 states the five conventions every artifact obeys; C.6 points at the companion ml-foundations/ ladder and says why it exists alongside the artifacts.

C.1 Why This Is an Index and Not a Listing

The 42 artifacts total 8,992 lines and 428,440 bytes of Python; the assembled ml-book.html is 1,810,756 bytes before appendices. Verify Those two numbers are the argument. Reproducing every listing here would take the book’s code content from roughly 428 KB to 857 KB — a clean doubling of the executable half of the book — and add about a quarter to the single HTML file the reader must load, scroll and search. Not one byte would be new: the listings already sit adjacent to the derivations they implement and to the paragraph quoting what they print.

The second cost is worse. Duplicated code drifts. The predecessor volume in this series carried this kind of duplicate appendix and it went stale: its part-and-chapter ranges stopped matching the real table of contents and a definition was cited to the wrong chapter, because it was maintained by hand against a book that kept moving. Every row below was generated by mechanical extraction from the assembled HTML, so the titles, chapter numbers and part groupings are the book’s rather than anyone’s memory of them.

What an index buys that a listing does not is lookup by intent: the backward pass checked against finite differences is Chapter 10’s, the KV cache checked against full recomputation is Chapter 18’s, the depth counting model is Chapter 38’s. That is a query the tables answer and 428 KB of pasted source does not.

Common Pitfall

Copying an artifact out of the rendered HTML without unescaping. The listings sit inside <pre><code>, so &lt; and &amp; appear as entities in the raw file. Browser copy-and-paste unescapes them; curl plus a regex does not, and the failure mode is a SyntaxError on the first comparison operator. Prefer code/: byte-for-byte the same source, verified listing-against-file for all 42 chapters. Certain

Each artifact is a standalone module ending in an if __name__ == "__main__": demo — all 42. Certain No artifact imports another: code/ holds 43 files, the 42 artifacts plus Chapter 11’s engine shipped separately as autodiff_engine.py with its own self-test, for you to import into your own work. To run one:

python code/ch18_artifact.py

C.5 Artifact Conventions

Five rules hold across all 42, and they are why the chapters’ numbers can be trusted.

Executed before written, re-run during fact-checking. Each artifact was written to a file, run to completion, and iterated until clean; only then was the source pasted into the chapter, and the paragraph following each listing quotes measured output from that run. Every artifact was then independently re-executed during fact-checking, from the extracted listing rather than the working copy. Wall-clock figures are tagged Verify, because timings are the one class of number a different machine will legitimately contradict.

Optional imports are guarded. The core of every artifact is NumPy. Cross-check libraries are imported inside try/except ImportError and the fallback prints a skip line rather than raising:

try:
    import torch
except ImportError:
    torch = None
    print("[skipped: torch not installed]")

35 of the 42 files contain at least one such skip path. Certain A missing library costs you a cross-check, never a run. The six SciPy hard dependencies above are the honest exception: SciPy does load-bearing work there — an L-BFGS-B fit, an inverse normal CDF — rather than confirming a result already computed.

One seed, stated explicitly. Randomness enters through np.random.default_rng with a literal integer seed, never the legacy global np.random.seed and never unseeded. Forty of the 42 artifacts draw random numbers, and every one of the forty constructs np.random.default_rng(0). Certain Eight of them open further streams with other small literal seeds where two experiments in the same file must not share one — Chapter 17 uses 0 through 6 across its decay sweep, Chapter 14 uses 1, 2 and 3 for its three exact-identity checks and 11 for its torch cross-check — and Chapter 14’s five ablation arms are instead averaged over the shared seeds 0, 1, 2, so the arms differ by regularizer and nothing else. Chapters 40 and 41 draw none at all. Reproducibility is bit-level on pure-NumPy paths and float64-rounding-level through BLAS, where thread count changes summation order.

Assertions print residuals, not verdicts. The 42 artifacts contain 300 assert statements. Verify A check that prints only OK hides how much room was left; every check here prints the measured quantity beside its threshold, which is what lets a chapter say a gradient matched torch to $4.4\times10^{-16}$ rather than merely that it passed at $10^{-6}$ — the difference between an exact derivation and one that is close enough today.

Self-verification is always against something external. No artifact checks itself against itself. Every assertion resolves to one of four independent references:

Reference classWhat it meansRepresentative artifacts
Finite differencesAn analytic derivative against a central difference quotient of the objective it differentiates6 (gradient and Hessian), 10, 11, 12, 15, 18, 20, 27
Brute forceA fast algorithm against an exhaustive enumeration too slow to ship, small enough to run1 (rank-$k$ search), 8 (all split candidates), 14 (all $2^{12}$ masks), 24 (400,001 allocations), 25 (all pairs), 42 (all DAG paths)
Closed formA simulation or fit against an analytic answer, the problem chosen so one exists2, 4, 5, 21, 27 ($\pi^\ast$), 28 (pass@$k$), 33, 35 (the exact score), 36, 38, 41
Reference implementationA from-scratch implementation against a mature library’s, weights transplanted so the comparison is of arithmetic5, 13, 16, 17, 18 (torch); 7, 8, 9 (scikit-learn); 29 (both)

The ordering matters. A closed form beats a reference implementation, because a library can be wrong and frequently changes; where neither exists, brute force beats a plausibility check. A reference implementation is the weakest of the four and is the sole check in none of the 42. Likely That is why several artifacts construct their problem so that an exact answer exists at all — Chapter 27’s 6-armed bandit and Chapter 35’s Gaussian-mixture target are chosen precisely so the thing being learned has a formula.

C.6 The Companion Ladder: ml-foundations/

Alongside the book sits ml-foundations/, an exercise ladder of 17 standalone files across seven tiers — tier0_math/ through tier6_encrypted/ — running from matrix calculus and floating point up to polynomial approximation and depth budgeting under encryption. Verify Tier 0 maps onto Parts I–II (Chapters 1, 2, 4, 5, 6), tier 1 onto Part III, tiers 2–3 onto Part IV, tier 4 onto Part V, tier 5 onto Part VI, tier 6 onto Part VIII. Run all of it, or one tier:

python3 check.py
python3 check.py tier0_math

The ladder follows the same dependency discipline — optional imports guarded, tiers 0–3 fully usable with NumPy alone — and uses the book’s confidence markers: TenSEAL and OpenFHE surfaces in tier 6 carry Verify, because those APIs move faster than any book.

The two are not redundant, because their intent is opposite. An artifact is a demonstration: complete, commented, runnable the moment you paste it, built to make a chapter’s claim checkable. You read it, run it, see that the residual against finite differences really is $10^{-10}$, and move on. Reading it is the point. A ladder exercise is a specification with a reference solution attached, and its README tells you to delete the function body, replace it with pass, and write it again from the docstring and the assertions below. The assertions are the specification; the reference implementation exists so you can check yourself, not so you can read it.

Reading an implementation and writing one are different skills, and only the second transfers. An artifact read carefully leaves you able to recognize the construct; an exercise reimplemented from an empty file leaves you able to build it. The ladder’s standard is the right one: an exercise is finished when you can delete it, wait a week, and write it again from the docstring. Likely None of the 42 artifacts is designed for that. Use them to verify what you have read; use the ladder to find out what you can write.
