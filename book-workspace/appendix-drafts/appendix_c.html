Appendix C

Complete Code for All Artifacts

Forty-two chapters, forty-two artifacts, one per chapter, always numbered N.1. Each is already printed in full inside the chapter that motivates it, which is the only place it makes sense to read it: the code is that chapter's evidence, and separating evidence from claim helps nobody. This appendix is therefore an index rather than a second copy — one table to find the artifact that builds the thing you need, what it checks itself against, and what you must have installed. Section C.1 explains why the second copy would be a defect rather than a convenience; C.2 is the index, grouped by part; C.3 states the four conventions every artifact obeys; C.5 points at the companion ladder in ml-foundations/, whose purpose is deliberately the opposite of an artifact's.

C.1 Why This Appendix Is an Index and Not a Listing

The book ships as one self-contained HTML file. At the last assembly of Chapters 1–37 that file was 1,611,677 bytes — call it 1.6 MB — of which 384,177 bytes, 23.8%, was already artifact source inside <pre><code> blocks. Verify The full 42-file corpus is 8,958 lines and 427,676 bytes of Python, which becomes 462,850 bytes once HTML-escaped. Reproducing it here would take the listings from 384 KB to roughly 847 KB, push the assembled file past 2 MB, and make code about 41% of the book by volume — a second complete copy of every line, differing from the first only in position.

That is not a stylistic objection. A single-file book is a usability contract: it opens offline, it is searchable with one browser find, and it survives being emailed. MathJax typesetting time and DOM construction both scale with document size, and the appendices load last. Doubling the code buys nothing but a second reading order. If you want the sources as files rather than as page elements, take them from book-workspace/code/, which is where they were executed from in the first place.

C.3 The Conventions Every Artifact Follows

C.3.1 Executed before written, re-run during fact-checking

No artifact was composed in an editor and pasted into the book. Each was written to a file, run, corrected until it ran clean, and only then transcribed — and the results paragraph after each listing quotes numbers from that run, not numbers the author expected. A separate fact-checking pass re-ran every file from a clean interpreter and re-read the quoted numbers against the fresh output; that pass is why several chapters carry corrections in the commit history. The corpus is 8,958 lines across 42 files, averaging 213 lines, shortest 143 (Chapter 36), longest 320 (Chapter 20). Verify

C.3.2 Optional imports are guarded

The core of every artifact is NumPy. Torch and scikit-learn appear only as cross-checks, and every such import sits inside a try/except ImportError that binds the name to None, with the dependent block printing a skip line rather than raising. Twenty-nine artifacts guard torch this way, five guard scikit-learn, three guard scipy. Six require scipy at module load — Chapters 3, 20, 24, 26, 27, and 33 — because it is doing real work there (Huber optimization, special functions, statistical tests) rather than checking someone else's. Certain A reader with only NumPy installed sees every artifact run to completion, with cross-check lines replaced by skip notices and every assertion about the from-scratch implementation still enforced.

A cross-check is not a dependency of the idea. If Chapter 13's Muon implementation is correct, it is correct whether or not torch.optim is installed to say so; refusing to run without torch would confuse “I cannot confirm this” with “this is wrong,” and would put a large wheel between the reader and a 275-line file.

C.3.3 One seed

Every artifact that draws random numbers seeds np.random.default_rng(0), and none calls the legacy global np.random.seed. Reruns are bit-identical on the same NumPy version, which is what makes the quoted numbers checkable at all. Three departures exist, and they are departures from the seed rather than from determinism. Chapter 14 uses several distinct seeds and averages an explicit sweep, because its subject is variance across seeds — a regularization ablation reported at one seed is reporting noise. Chapters 40 and 41 draw no random numbers at all: one is a sourced record database, the other a deterministic counting model.

C.3.4 Self-verification, and what does not count

Every artifact asserts something and prints the measured residual rather than the word OK. The assertions fall into four families; most artifacts use two or three.

ModeWhat it establishesRepresentative chapters
Finite differencesAn analytically derived gradient, Jacobian, or Hessian matches numerical differentiation of the function it claims to differentiate.6, 10, 11, 18, 20, 27
Brute forceA fast or vectorized construction returns what an obviously correct but intractable enumeration returns, on instances small enough to enumerate.1, 8, 14, 22, 25, 31
Closed formA measured quantity equals an independently derived formula — an exact iterate, an optimal policy, an acceptance rate, an analytic score field.4, 17, 24, 32, 33, 35
Reference implementationThe from-scratch version agrees with a mature library given identical weights and hyperparameters, to a stated tolerance.5, 7, 9, 13, 16, 29

What is absent from that list is the point: no artifact verifies itself against itself. Certain Comparing a vectorized implementation to a loop that calls the same helper proves only that the helper is deterministic. Two artifacts say so in their own headers. Chapter 41 notes that the chapter's closed forms are checked against the simulator rather than derived from it. Chapter 1 rejects a random $UV^{\top}$ product as an Eckart–Young competitor in favour of 5,000 rank-$k$ candidates each optimally refitted inside its own random column space — a much stronger adversary, and therefore a much stronger result when the optimum still wins.

Common Pitfall

The easiest way to fake a passing test is to derive the expected value from the code under test. If the “analytic” FLOP count is produced by the same function that instruments the run, the assertion is a tautology; if the tolerance is set just above the observed error, the assertion encodes the bug. The rule here: the expected value must come from a source that could disagree — a paper's formula, a library, an enumeration, a hand ledger written before the run — and the tolerance must come from the arithmetic (machine epsilon, condition number, sample size) and be reported next to the residual so the margin is visible. Chapter 15 is the model: it asserts the muP optimum does not move at all and that the SP optimum moves by at least a factor of four, a prediction that could have failed.

C.4 Running Them

The sources live in book-workspace/code/, one file per chapter, named by chapter number. Each is standalone with an if __name__ == "__main__": demo, takes no arguments, downloads nothing, and synthesizes its own data. Appendix B covers the environment; the short version is NumPy, plus SciPy for the six chapters that need it, plus torch and scikit-learn if you want the cross-checks to fire rather than skip.

# one artifact
python book-workspace/code/ch18_artifact.py

# all of them, each in its own interpreter, echoing the filename first
find book-workspace/code -name 'ch*_artifact.py' | sort | xargs -n1 -t python

Each finishes in well under a minute on a laptop CPU; the slowest are the training-loop artifacts in Chapters 14, 20, and 35. Verify A missing cross-check library produces a skip line and the run continues. A firing assertion is a real disagreement between the code and the book, and the failing residual prints with it.

C.5 The Companion Ladder, and Why It Is Different

Alongside the book, ml-foundations/ is an exercise ladder: standalone Python files in seven tiers, from matrix calculus and floating point through autodiff, architectures, sequence models, LLM training, systems, and finally polynomial approximation and depth budgeting under encryption. Verify It is paced by study-plan.html, and python3 check.py runs the whole ladder, or one tier.

The intent is the opposite of an artifact's. An artifact demonstrates. It is complete, printed in full, and its job is to make a claim checkable — you read it the way you read a proof and run it to confirm that the numbers in the surrounding paragraph are real. Withholding anything would defeat the purpose. A ladder exercise is meant to be deleted and reimplemented. Each file ships with a working reference implementation and a block of check() assertions, and the instruction is to replace a function body with pass, re-read the docstring and the assertions, and write it again yourself. The assertions are the specification; the reference implementation is the answer key you are supposed to stop looking at.

This is not redundancy but the split between two skills that feel identical and transfer differently. Reading a correct implementation produces the sensation of understanding almost immediately and reliably overestimates it, because good code hides its difficulty — the gaps that matter are the ones a well-written listing makes invisible. Writing one against a fixed test surfaces them in minutes. Likely The evidence is pedagogical rather than settled: the generation and testing effects are robust in the memory literature, and their application to programming specifically is plausible, not proven.

The recommendation is therefore asymmetric. Read every artifact — you cannot check the book's claims otherwise, and several contain the only complete statement of a construction the chapter treats in pieces, Chapter 19's RoPE equivalence and Chapter 21's four-way SSM agreement being the clearest cases. But do not mistake having read them for being able to write them. For that, take the matching tier, delete the bodies, and find out. The ladder is coarser than the book — one exercise often spans two chapters — and its README tier table names the mapping, while the study plan sequences both together across 42 weeks.
